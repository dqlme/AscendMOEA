# 安装与运行故障定位

## 诊断顺序

出现异常时按四层定位：环境、设备、数值、算法。先保存失败任务配置、日志和最小输入，
不要直接在原结果目录覆盖重跑。

## 导入与安装

### `ModuleNotFoundError: ascendmoea`

确认当前 Python 与安装命令属于同一环境：

```bash
which python
python -m pip show AscendMOEA
python -c "import ascendmoea; print(ascendmoea.__file__)"
```

### 实际问题找不到 MAT 数据

列出 wheel 内容并确认 `ascendmoea/vendor/**/*.mat` 已包含。若源码可运行而安装包失败，
通常是 package-data 或资源访问方式错误。

## NPU 不可用

```bash
npu-smi info
python -c "import torch_npu, torch; print(torch.npu.is_available())"
```

检查驱动、固件、CANN、PyTorch 与 `torch_npu` 版本组合，以及两个 CANN 环境脚本是否
已加载。不要通过普通 `pip install torch` 覆盖设备版 PyTorch。

## CPU 进程出现在 NPU0

根因通常是 PyTorch 后端自动加载。必须在第一个 `import torch` 之前设置
`TORCH_DEVICE_BACKEND_AUTOLOAD=0`，并保证 CPU worker 显式使用 `device="cpu"`。
修复后重新运行 CPU 基准，因为原时间和内存已受到 NPU 初始化污染。

## NPU 比 CPU8 慢

逐项检查：

1. `N` 和每代张量是否太小；
2. 计时是否包含首次图/算子编译；
3. 是否在循环中调用 `.item()`、`.cpu()` 或 `.numpy()`；
4. 目标函数或算法是否仍逐个个体循环；
5. 是否频繁创建 CPU 常量后复制到 NPU；
6. 多个 worker 是否共享同一张卡；
7. 算子是否落到 CPU fallback；
8. NPU 利用率和功耗是否长期很低；
9. `max_fe` 是否被错误设置，导致设备间实际工作量不同；
10. 计时末尾是否同步。

先用 profiler 或分段计时找出代内瓶颈，再决定向量化、缓存、减少同步或提高规模。单纯加大
`max_fe` 只会重复同一个低效路径，不能修复结构问题。

## 内存异常

### RSS 总和很大

多进程共享库会被每个 RSS 重复统计，应查看 PSS。再按进程树区分主 worker、joblib 子
进程、CANN 编译进程和监控器。

### NPU HBM 持续增长

检查历史监控器是否把 NPU 种群全部保留、算法缓存是否跨代累积、Python 引用是否阻止
张量释放。正式历史应及时迁移 CPU 并流式落盘。

### `O(N^2)` 算子 OOM

支配矩阵和距离矩阵内存随种群平方增长。记录 dtype 与所有中间布尔/浮点矩阵，降低不必要
的重复张量。若研究设置超出单卡容量，可开发保持相同数值语义的分块版本，但不能悄然
改变平局或截断语义。

## 指标异常

- NaN：检查目标、参考集、归一化分母和空可行种群。
- HV 为 0：检查参考范围、最小化方向和归一化后是否全部越界。
- IGD 很大但前沿图正常：检查目标列顺序和参考前沿维数。
- IGDX 异常：确认传入的是决策空间参考集，不是目标前沿。
- 可行率为 0：检查约束符号是否应为 `<= 0`，以及等式容差。

## 队列似乎卡住

不能只看单次任务运行时长。检查：

- 进度文件最后更新时间；
- 进程 CPU 活动、I/O 和 NPU 利用率；
- 当前算法/问题历史中位时间；
- 日志是否仍增长；
- 是否在模型编译或大规模 HV 计算。

只有心跳超时且进程无活动、日志无增长并超过问题级超时阈值时，才判定挂死。终止前保存
进程树、设备状态、栈和当前任务。

## 最小复现模板

每个故障应缩减为：固定一个算法、一个问题、一个 seed、一个设备、最小仍可复现的 `N`
和 `max_fe`。保存包版本和完整环境；恢复运行后，只重排受影响的正式任务。
